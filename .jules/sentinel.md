## 2025-01-24 - Centralized Write Protection for Critical DLLs
**Vulnerability:** Lua scripts could potentially overwrite or delete the library itself (`bzfile.dll`) or other sensitive shims like `winmm.dll`, even if `g_AllowWinmmOverwrite` was only intended to control `ReplaceFileOnExit`.
**Learning:** Security checks were inconsistently applied across different filesystem operations (`Open`, `CopyFile`, `Delete`, `ReplaceFileOnExit`). `Delete` and `Open` (for writing) had no protection against targeting critical DLLs.
**Prevention:** Centralize write-protection logic into a single helper (`IsWriteProtected`) and ensure it is called by all functions that can modify or remove files.

## 2026-09-27 - Write protection covered two names and could be switched off
**Vulnerability:** `IsWriteProtected` matched only `winmm.dll` and `bzfile.dll` by exact leaf name, and any mission script could disable it for the whole process with `bzfile.SetAllowWinmmOverwrite(true)`. `bzloader.dll`, `openshim.dll`, the helper, the game exe, `net.ini`, `patches.json` and the helper's staged/backup files were writable; `winmm.dll::$DATA` and `winmm.dll.` reached `winmm.dll`; `MakeDirectory` never checked; `ReplaceFileOnExit` let a script pick any destination for a deferred, unverified replacement. `CopyFile(src, dst, true)` deleted `dst` before knowing the copy could succeed.
**Learning:** A centralized check is only as strong as its rule and its off switch. Matching literal names misses the spellings Windows resolves to the same file, and a Lua-reachable toggle turns the whole policy into a suggestion.
**Prevention:** The rule lives in `src/bzfile_write_policy.h` (all native code by extension, suite configuration, transaction files; names normalized the way Win32 resolves them) and is host-tested. It has no off switch. Destructive operations stage beside the target and rename into place. `tests/Test-LuaHost.ps1` exercises every mutating binding through real Lua in CI.
